## [Unreleased]

### Added

- **apps/swifty**: End-to-end image support — the model can now see images from `ReadFile`, `@image.png` mentions, and MCP tools, on both Anthropic and OpenAI providers, with session persistence and compaction fully image-aware.
  - **Core design — content blocks, not sidecar fields**: multimodal payloads ride in the existing content channel as a union type. `ToolResult.output`, `ToolResultBlock.content`, `Message.content`, and the `tool_result` `AgentEvent.output` are all `string | Record<string, unknown>[]`, where blocks use the provider-agnostic shape `{type:"text", text}` / `{type:"image", source:{type:"base64", media_type, data}}`. Text-only flows keep plain strings (zero overhead, byte-identical provider requests); every display-only consumer flattens block arrays through one shared helper, `contentToText` (`src/utils/index.ts`), which renders images as `[image: <media_type>]` placeholders. The union type makes the compiler enforce that each consumer explicitly handles the block case.
  - **Image processing layer (`src/images/`)**:
    - `detect.ts` — extension→media-type mapping and magic-bytes sniffing for png/jpeg/gif/webp; magic bytes win over the extension when they disagree.
    - `limits.ts` — 5 MB base64 API limit, 3.75 MB raw passthrough target (base64 inflates by 4/3), 2000 px max dimension, JPEG quality ladder `[80, 60, 40, 20]`, and a 10-images-per-message cap.
    - `resize.ts` — `maybeResizeAndDownsampleImage`: small images pass through byte-identically (sharp never consulted); oversized ones are resized to fit 2000 px and recompressed (PNG preserved at compressionLevel 8 + palette when it fits, otherwise the JPEG quality ladder); incompressible inputs throw `ImageTooLargeError` with size context.
    - `load.ts` — `loadImageAttachment`: stat → sniff → compress; errors carry actionable messages.
  - **`ReadFile` on images** (`src/tools/read-file.ts`): image paths return `[label text block, image block]` — the label (`[image: <name> · <media_type> · <size>]`) anchors the image to its file for the model and gives text-only consumers a useful line. The read is recorded in `fileStateCache`; `offset`/`limit` do not apply; an image-extension file with non-image bytes errors out. The tool description documents the capability.
  - **`@image.png` mentions in the TUI** (`src/tui/at-expand.ts`, `src/tui/app.tsx`): `expandAtRefsWithImages` loads image refs through the resize pipeline as inline image blocks and appends an `<image type="base64" media_type="…" path="…"/>` placeholder to the text so the model can pair each attachment with its token; exceeding the 10-images-per-message cap appends an inline error note, while a failed load is logged and dropped; non-image refs (including `#L3-10` ranges) behave exactly as before; with no image involved it returns a plain string. On submit the conversation receives the expanded blocks, the session stores the original typed text plus the image blocks, and the UI keeps showing exactly what the user typed.
  - **MCP tool images** (`src/mcp/client.ts`): `mcpContentToToolOutput` converts MCP `{type:"image", data, mimeType}` content (png/jpeg/gif/webp) into provider-style blocks, recompressing oversized payloads through the shared pipeline (dropping, with a text note, anything that cannot fit the API limit); unsupported mime types keep their JSON text form; text-only results remain plain strings.
  - **Agent loop** (`src/agent/agent.ts`, `src/agent/events.ts`): `tool_result` events carry the structured output end-to-end, so blocks enter the conversation intact; image results are exempt from both the single-result spill (`MAX_OUTPUT_CHARS`) and the aggregate tool-result budget (`src/tool-result/budget.ts`) — they must reach the API as-is; the `ReadFile` recovery snapshot skips image outputs (binary would poison the utf-8 snapshot); post-tool hooks receive flattened text.
  - **Anthropic** (`src/llm/anthropic.ts`): user content blocks pass through natively; tool_result block arrays are sent inside the `tool_result` content; the consecutive-user merge (post-compaction alternation repair) accepts image-carrying messages on either side; `markLastUserTailForCache` puts `cache_control` on the last non-image block (some gateways reject it on image blocks) and falls back to the true tail when every block is an image.
  - **OpenAI** (`src/llm/openai.ts`), both endpoints: user image blocks become `input_image` (Responses) / `image_url` (Chat Completions) data-URL parts after the text; since `function_call_output` / `role:"tool"` content is text-only, tool images ride in a synthetic user message — `[Image(s) returned by tool call <id>]` followed by the image parts — appended after the whole output batch so call/output pairing stays contiguous; block arrays without images never emit a dangling header.
  - **Compaction** (`src/compact/compact.ts`): token estimation counts every image block at a fixed 7000-char equivalent (~1750 tokens) in both message content and tool results, so image-heavy conversations compact on time instead of overflowing; the summarizer prompt flattens blocks to text placeholders (a text-only summarizer never sees base64).
  - **Display & serialization consumers** flatten via `contentToText`: TUI tool summaries, resume replay, memory recall/extraction and fork snapshots; remote WS `tool_result` broadcast and session replay; `-p` stream-json output; team transcripts; teammate fork-marker scanning guards on string content.
  - **Verification**: typecheck and eslint clean; 271 vitest tests across 36 files, including an end-to-end wiring test (image blocks through the agent loop → session JSONL → resume restores the exact base64), provider-builder tests for both endpoints, `@image` expansion, `ReadFile` image behavior, MCP conversion, compaction estimates, and cache-marking edge cases.
  - Scope notes: images enter through `ReadFile`, `@` mentions, and MCP tools; the web UI input remains text-only. Supported formats: png/jpeg/gif/webp.

- **apps/swifty**: VSCode integration — select code in the editor and press `Cmd+Option+K` (macOS; `Ctrl+Alt+K` elsewhere) to insert a `@path#L3-10` reference into the CLI input box. Implemented by reusing the already-installed `anthropic.claude-code` VSCode extension's embedded WebSocket MCP server; the extension side needs no changes and swifty ships no extension of its own.
  - New module `src/vscode/` (3 files):
    - `lockfile.ts` — service discovery. Scans `~/.claude/ide/<port>.lock` (honors the `CLAUDE_CONFIG_DIR` env override), validates lockfile JSON with a zod schema (`workspaceFolders`, `pid`, `ideName`, `transport`, `authToken`), and picks the extension instance for this terminal: first by `CLAUDE_CODE_SSE_PORT` env match (injected by the extension into its integrated terminals), falling back to an unambiguous cwd-inside-workspaceFolders match (NFC-normalized for macOS NFD paths). Only `transport: "ws"` lockfiles are supported.
    - `ws-transport.ts` — an MCP `Transport` implementation over `ws` (the MCP SDK ships no WebSocket client transport), connecting with subprotocol `mcp` and explicitly converting `RawData` (`Buffer | ArrayBuffer | Buffer[]`) to utf-8 before JSON parsing.
    - `ide-client.ts` — `connectToIde()`: polls discovery for up to 30s when inside an IDE terminal (`CLAUDE_CODE_SSE_PORT` set or `TERM_PROGRAM=vscode`), authenticates with the `X-Claude-Code-Ide-Authorization: <authToken>` header, announces itself with an `ide_connected { pid }` notification (the extension routes the keybinding to the CLI whose pid sits in the active terminal's process tree), and registers a handler for `at_mentioned { filePath, lineStart, lineEnd }` notifications (0-based lines, converted to 1-based). Note: the extension sends a file-path/line-range reference, not the selected text itself.
  - `src/tui/input.tsx`: `InputBox` gained an `insertTextRef` prop exposing an insert-at-cursor function (pads a leading space when the preceding character is not whitespace), enabling programmatic text injection without refactoring the component.
  - `src/tui/app.tsx`: connects on mount (a successful connection is only logged by the IDE client — no TUI system message), and turns each `at_mentioned` notification into `@<relative-path>#L<start>[-<end>]` inserted at the input cursor.
  - `src/tui/at-expand.ts`: `expandAtRefs` / `expandAtRefsWithImages` now parse an optional `#L3` / `#L3-10` suffix and inline only the referenced lines as `<file path="…" lines="3-10">…</file>` at submit time (files up to 10 MB are sliced; the resulting snippet still honors the 100 KB inline cap).
  - Caveat: this depends on the third-party extension's undocumented protocol (lockfile format, auth header, notification methods), which may change without notice; if another Claude-compatible CLI runs in the same window, the extension routes the keybinding by terminal pid.

### Changed

- **install.sh**: `npm install -g` now runs with `--force`, and legacy standalone global packages (`@swifty.js/swifty`, `@swifty.js/swiftx`) are uninstalled before installing larky. Fixes `EEXIST: file already exists` on the `swifty`/`swiftx` bin links left behind by previous installs.
- **apps/larky**: dependencies on `@swifty.js/swifty` and `@swifty.js/swiftx` changed from `workspace:*` to `latest`, so fresh installs of `@swifty.js/larky` always resolve the newest swifty/swiftx without republishing larky on every dependency release. Root `package.json` gained `pnpm.overrides` mapping both packages back to `workspace:*` so local monorepo installs keep linking the workspace sources (overrides are dev-only and not published).

- **apps/swifty**: Removed the content-addressed session image store (`src/images/store.ts`, `.swifty/sessions/<id>/images/`). Image blocks are now persisted inline as base64 in the session JSONL (matching how tool results already flow to providers), and resume reads them straight back — no `image_ref` indirection. `saveMessage`, `toolResultsToRecords`, and compaction boundary writes persist content verbatim; `persistableContent`, `sessionCtxFromFilePath`, and the expired-session `images/` cleanup were deleted along with the store.

### Known Issues

- **Environment-dependent tests (not yet fixed)**: Several test files in `apps/swifty` read the real user home directory instead of an isolated one. They currently pass, but their assertions are sensitive to user-global state and may fail or produce false positives on machines with certain `~/.swifty` contents:
  - `tests/memory.test.ts` — `MemoryManager.buildSystemReminder()` also scans `~/.swifty/memory`; the "no WARNING below the 200-line cap" assertion can flip once a user's global memory entries push the combined index past the truncation threshold.
  - `tests/skills.test.ts` — `SkillCatalog.load()` also scans the global skill directories (`~/.claude/skills`, `~/.github/skills`, `~/.swifty/skills`); a user-global skill whose name collides with a fixture (e.g. `audit-deps`) would shadow or corrupt the lookup-by-name assertions.
  - `tests/instructions.test.ts` — `loadInstructions()` also reads user-global `~/.swifty/SWIFTY.md` / `~/.swifty/AGENTS.md`; assertions rely on `toContain` and relative ordering and would break if user-global content collides with fixture markers.

  Planned remediation: adopt the existing `HOME`/`USERPROFILE` redirection pattern (see `tests/teams.test.ts`) in these files.
